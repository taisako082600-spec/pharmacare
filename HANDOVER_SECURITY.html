§1規制は3層に分かれている

混ぜると判断を誤ります。「ガイドラインで求められている」は法的義務ではありません。

層例強制力名宛人
法律個人情報保護法、薬機法、e-文書法あり（罰則）事業者・提供者
ガイドライン厚労省 医療情報システム安全管理GL、3省2ガイドラインなし医療機関等／提供事業者
取引条件顧客の導入審査、Pマーク提出要求なし（ただし受注できない）交渉次第

個人情報保護法の委託先監督義務は顧客（施設）側の義務で、提供者の義務ではありません。提供者自身の法的義務は安全管理措置を講じること（23条）まで。第三者認証の取得義務は法律上ありません。

別軸で最も重いのは薬機法

プログラムが「疾病の診断・治療・予防」を目的とするとプログラム医療機器に該当し、製造販売業許可と承認／認証が必要になります。無許可販売は違法（罰則あり）。セキュリティとは独立した論点で、企画段階で該当性を確認すべきものです。

§2認証は「指定された施設のみ」ではない

個人事業主法人備考
Pマーク申請可能可能法人番号が無い場合、開業届または直近2期の決算書で代替
ISMS (ISO/IEC 27001)申請可能可能組織単位の審査

法人格は要件ではありません。詰まるのは別のところです。

実際の障壁は「体制」

どちらの認証も、技術が優れていることを見る制度ではありません。組織として回っているかを見ます。

  • 内部監査の独立性 — 自分で作って自分で監査する状態は認められない。1人だと外部委託が要る
  • 教育の記録 — 従業者への年次教育とその証跡
  • 規程類 — 基本方針、取扱規程、委託先管理、事故対応
  • 運用実績 — 作った直後では審査に出せない。数ヶ月〜の運用記録が要る

つまり「実力次第で個人でも取れる」は半分正しい。技術力では取れませんが、体制を作れば個人事業主でも取れます。費用はPマークで30〜80万円＋審査費用、期間は半年〜1年が目安です。

「会社として通用するレベル」の実像

顧客の導入審査で実際に問われるのは、認証の有無だけではありません。

  1. 委託先としての適格性を開示できるか（3省2ガイドライン 表4-1 に対応した文書）
  2. データの所在 — どのリージョンに置き、なぜそこか
  3. バックアップと復旧 — 復元可能な期間、手順書
  4. 監査ログ — 誰がいつ何を見たか。顧客自身が確認できるか
  5. 事故時の連絡体制
  6. 賠償責任保険 — 個人事業主だと未加入が多く、ここで止まることがある
  7. 第三者評価の有無 — 無い場合、代替の説明ができるか

認証が無くても、1〜6が揃っていれば受注できる案件はあります。逆に認証だけあって1〜6が無いと審査で詰まります。順序としては1〜6が先です。

§3設計原則

ファーマケアで見つかった脆弱性はすべて同じ形をしていました。次は最初から避けられます。

原則1　権限を決めるフィールドを、本人に書かせない

悪い： users/{uid}.isAdmin を本人が更新できる
       → isAdmin() がそれを読んで判定している
       → 自分に true を書けば管理者になれる

同じ構造で3件ありました。isAdmin（全施設の患者が読める）、facilityId（任意の施設の患者が読める）、linkedPatientId（誰でも任意の患者の家族になれる）。

チェック方法：権限判定に使っているフィールドを列挙し、それぞれ「誰が書けるか」を確認する。

原則2　create と update で判定が違う

悪い： 差分(diff)で禁止フィールドを守る
       → 差分は「既存ドキュメントとの比較」なので update にしか効かない
       → 新規作成は素通し

linkedPatientId はこれで抜けていました。差分ベースの防御を書いたら、必ず create 側も別に書く。

原則3　クライアント側の検証は、無いのと同じ

招待コードの検証がDartにしか無く、サーバーは「facilityIdが書かれていれば信じる」状態でした。

解法：ルール内の get() は read 権限を経由しないので、クライアントに読ませないまま照合できます。そのためには照合先をIDで引ける形にしておく必要があります（コード文字列そのものをドキュメントIDにする、{userId}_{facilityId} のような決定的IDにする）。設計時に決めておくと後が楽です。

原則4　攻撃と正規操作の両方をテストする

締めすぎて正規の操作が壊れるほうが、実運用では穴より先に問題になります。ファーマケアのルールテストは16ケースで、うち5件は「通るべき操作」です。

ルールテストAPIで更新を検証するときは、更新前のドキュメント（testCase.resource）を渡さないと diff() が評価できず、正当な操作まで DENY と出ます。これで一度誤読しました。

原則5　仕様書と実装がずれる

  • 開示書に「二要素認証は任意設定、登録者0名」とあったが、実装は必須化済みだった
  • READMEに「本番ビルドはCloud Run URLを埋め込み済み」とあったが、埋め込まれていなかった

顧客に見せる文書ほど、コードから生成するか、変更時に必ず突き合わせる。

§4「動いているつもり」を潰す

この案件で一番大きかった不具合は、脆弱性ではなくこれです。

服薬注意点の機能が、一度も動いたことがなかった。プロキシURLを --dart-define で渡す設計で、渡し忘れたビルドが本番に出ていた。全端末が自分自身の localhost:8081 を叩いていた。

画面には「プロキシに接続できません」としか出ないので、実機のスクリーンショットを見るまで誰も気づけませんでした。

対策

  1. 既定値は本番を指す。開発環境のほうを上書きする（逆にしない）
  2. デプロイ時に機械が止める。成果物に開発用の向き先が残っていたら中止
  3. 配信中の成果物を直接確認する
curl -s https://<site>/flutter_bootstrap.js | grep -o 'main\.dart[^"]*\.js'
curl -s https://<site>/<その名前> | grep -c 'localhost'

同種のものが他に3件ありました。呼び出し元が無い関数は、壊れていても気づけません（施設の監査ログ取得は documentId == facilityId で照合しており、常に0件を返す実装でした）。

§5AIと人のチェックの分担

この案件の実績で書きます。感想ではなく記録です。

AIが見つけたもの

6件

権限昇格3件（isAdmin / facilityId / linkedPatientId）ルールを1行ずつ読み、権限判定の入力になるフィールドを追跡
本番が全端末localhostを叩いていた配信中のバンドルを落として grep
新規施設の作成が拒否されていたルールが要求するフィールドを、クライアントが書いているか照合
薬剤師の承認が常に失敗していた同上
監査ログ取得クエリが常に0件条件式の意味を読んだ
添付文書11.2の表構造が抽出で壊れる実データで抽出して中身を見た

共通点：網羅性と、機械的な照合。人が「ここは大丈夫だろう」と飛ばすところを飛ばさない。

AIが外したもの

4件

PMDA検索の失敗を「全角のせい」と推定半角でも失敗した。実測せずに仮説を書いた
注意点が出ない原因を「APIキー未設定」と推定URLが原因だった。もっともらしい方に飛びついた
ルールテストのケース③自体が誤り「自分が作った施設なら通る」が正しい挙動だった
JSONの検証を「一部を切り出して parse」で済ませた周囲が壊れていても通る検証だった

共通点：もっともらしい仮説を、検証せずに結論として書く。実測すると外れる。

人が決めたこと

4件

「PMDA検索は一般名がいい」ドメイン知識。実測とも一致した
11.2は入れないスコープ判断。表が壊れた状態でLLMに整理させる危険を避けた
「一番見たいのは介護している人では？」利用者理解。薬剤師限定の実装を作り直させた
資料の構成、登録手順を概要の枠として使う伝え方の判断

この分担が噛み合う理由

  • AIは網羅性で強く、確信度の較正で弱い。「全部見る」は得意、「これは自信がない」と言うのは苦手
  • 人は判断で強く、網羅で弱い。118項目を1つずつ照合するのは向かない

したがって AIに全部読ませ、結論は必ず実測か人の判断で確定させるのが噛み合います。

実務上のルール

  1. AIの出す原因究明は、必ず実測で裏を取ってから修正に進む（仮説をコミットメッセージに書かない）
  2. AIが作ったテストも疑う。テストのほうが間違っている可能性を検討する
  3. 判断（スコープ・優先順位・利用者にとっての意味）は人が持つ
  4. AIが「検証しました」と言ったら、何をどう検証したかを確認する

優位性として言えること

  • 網羅的なレビューを毎回できる。人力だと工数が合わない
  • 見つけた穴の再現手順とテストを同時に作れる（この案件ではルールテスト16件が残った）
  • 判断の理由をコメントと履歴に残せる。引継ぎと監査に効く

ただし「AIが見たから安全」は成立しません。上のとおり外します。AIが網羅し、人が確定させるという工程そのものが成果物です。

§6新規プロジェクトの初期チェックリスト

企画

コードを書く前

  • 薬機法の該当性を確認する。診断・治療に関わる出力があるなら、企画段階でPMDA／薬務課に相談
  • 誰の情報を、誰から預かるのかを整理する（要配慮個人情報か）
  • 自分が委託先なのか、個人データを取り扱わない立場なのかを決める
  • データの所在（国内リージョン）を決める
設計

権限とログ

  • 権限判定に使うフィールドを列挙し、書き込み権限を分離する
  • 照合が必要なドキュメントはIDで引ける形にする
  • create と update の両方で検証する
  • 監査ログの設計（誰が・いつ・何を・変更前後）と、顧客が自分で見られる導線
実装

壊れていることに気づける状態

  • 権限ルールのテストを、攻撃と正規操作の両方で書く
  • デプロイ時に開発用の向き先が混ざっていないか機械で止める
  • 配信中の成果物を直接確認する手順を持つ
受注

審査で聞かれるもの

  • 情報セキュリティ基本方針・取扱規程
  • 委託先適格性の開示書（3省2ガイドライン 表4-1 対応）
  • 事故対応手順
  • 賠償責任保険
  • （必要なら）Pマーク／ISMS。体制が先、認証は後
