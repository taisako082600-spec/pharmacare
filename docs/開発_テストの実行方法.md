# テストの実行方法

このプロジェクトにあるテストと、その走らせ方。

> 以前ここにあったのは「QR読み取り（テストモード）」など**手動テストの手順書**でしたが、
> テストモードは実装に存在せず、**そのとおりに実行できない状態**だったため差し替えました。

---

## 全部走らせる

```bash
flutter analyze --no-pub          # 静的解析。エラー0であること
flutter test                      # Dartの単体テスト
node test_rules.js                # Firestoreの権限ルール
cd llm-proxy && go test ./...     # Goプロキシ
```

---

## Dart 単体テスト

```bash
flutter test
```

| ファイル | 内容 |
|---|---|
| `test/password_policy_test.dart` | パスワード要件（13文字以上・英数字混在・脆弱パターン拒否） |
| `test/invite_code_test.dart` | 招待コードの生成・正規化・表示形式 |

招待コードのテストには、**紛らわしい文字（I・L・O・0・1）が生成されないこと**の確認が
入っています。紙に書いて渡す運用があるためで、消すと入力ミスの問い合わせに化けます。

---

## 権限ルール（最重要）

```bash
node test_rules.js
```

Firebase の Rules テストAPIに実際のルールをかけ、**16ケース**を検証します。
実アカウントを作らずに「この認証状態でこの操作は通るか」を確かめられます。

**攻撃だけでなく、通るべき操作も入れてあります**（16件中5件）。
締めすぎて正規の操作が壊れるほうが、実運用では穴より先に問題になるためです。

ハマりどころが2つあります。

- 更新の検証では **`testCase.resource`（更新前のドキュメント）を渡さないと `diff()` が
  評価できず、正当な操作まで DENY** になります
- ルール内の `get()` / `exists()` は実データを見ません。**`functionMocks` で
  返り値を明示**する必要があります

**ルールを変えたら必ず走らせること。** 権限の穴は書いた本人には見えません。

## Go プロキシ

```bash
cd llm-proxy
go vet ./...
go test ./...
```

通常のテストのほかに、**環境変数を立てたときだけ走る調査用テスト**があります。
外部サイトへアクセスするため、既定では skip します。

```bash
PMDA_LIVE=1 go test -run TestPMDALiveProbe -v ./...
# PMDA検索を実際に叩き、販売名と一般名のどちらでヒットするかを確かめる

SECTION_PROBE_HTML=<保存したPMDAのHTML> go test -run TestSectionSizeProbe -v ./...
# 添付文書の各セクションの分量を測る
```

## デプロイ前

`node deploy.js` が成果物を検査し、開発用の向き先（`localhost:8081` など）が
残っていればデプロイを中止します。テストではありませんが、
**人が忘れうる手順を機械が止める**仕組みとして同じ役割を持ちます。

配信されたものの確認方法は [運用_デプロイと障害対応.md](運用_デプロイと障害対応.md) を参照してください。
